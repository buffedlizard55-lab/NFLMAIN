Sources & verification

Everything below is read from the build manifest, so it describes the snapshot you are actually looking at — not a hand-written claim.

The rule this project runs on

Every score, statistic and play here is produced by an automated pipeline from an NFL-sourced feed. Nothing is typed in by hand and nothing is estimated unless the field name says so. When the upstream data does not contain a value, the site shows — rather than a zero or a plausible guess, because “0 points” and “unknown” are different facts. Anything the pipeline thinks looks wrong is written into the irregularities table instead of being quietly repaired.

Provenance chain

  1. NFL clubs and on-field officials record the game.
  2. NFL GSIS — the league's Game Statistics & Information System, its official stat-keeping system. Stat identifier definitions are published by the NFL at nflgsis.com.
  3. api.nfl.com — the NFL's own API, the service that powers nfl.com. It answers HTTP 401 without an OAuth token the league issues to nfl.com and to contracted partners.
  4. nfl.com, read directly — the official public site. Two parts of it are read by this pipeline itself, with no credentials and no intermediary: the week page at /schedules/{season}/by-week/{week}, whose game tiles carry the league's own score and status (published under docs/data/official/ and diffed against everything here), and the league's Game Book PDF at /image/upload/gamecenter/{nfl_api_id}.pdf, linked on every game page whose NFL game UUID is known.
  5. nflverse — a mirror that scrapes nfl.com. The R package {nflfastR} is documented on CRAN as “Functions to access National Football League play-by-play data from https://www.nfl.com/”. Crucially it preserves the NFL identifiers old_game_id (GSIS 10-digit) and nfl_api_id (NFL API game UUID).
  6. This repository — pipeline/ normalises those feeds into docs/data/, which this site reads.

Why the mirror is in the chain at all: the NFL does not operate a free public developer API. The mirror is the only freely redistributable copy whose declared upstream is nfl.com itself, and it carries the real NFL identifiers. The identifier linkage was proven independently — see identifier proof.

Identifier proof

A mirror is only trustworthy if its IDs really are the league's IDs. This was checked rather than assumed:

  • The play-by-play feed reports nfl_api_id = a9a87603-4feb-11f1-abca-2c54536568a9 for game 2026_01_ARI_LAC (GSIS id 2026091308).
  • The official page nfl.com/games/cardinals-at-chargers-2026-reg-1 — a URL this project constructs from a verified pattern — resolves to “Arizona Cardinals at Los Angeles Chargers 2026 REG 1 - Game Center”.
  • That page's Download Game Book (PDF) link is static.www.nfl.com/image/upload/…/gamecenter/a9a87603-4feb-11f1-abca-2c54536568a9.pdf.
  • That verified UUID is now used: the Game Book is also served without its Cloudinary version stamp, so this pipeline builds the URL itself and links it on the game page. Fetched on 2026-09-25, it returned the NFL's own document — quarter line AZ 7/6/3/10 = 26 and LAC 7/0/7/0 = 14, the eight official scoring plays, and the final individual statistics, all matching this project's record for that game.
  • One identifier is not what its name suggests. The schedule feed's nfl_detail_id is not the NFL API game UUID, and it does not key the Game Book. 2021_01_DAL_TB reports 10160000-0585-0395-7f87-0c3334b38e2e while its official page links c5722300-b37c-11eb-9617-afa9727fab42.pdf; 2021_01_JAX_HOU likewise. Building a link from that column produced URLs that cannot work, so it is stored under its own name and never used to build one. The whole finding is published below with its evidence.

The league's own Game Book is keyed by exactly the UUID the play-by-play feed reports, so the linkage is genuine and every record here can be traced to an official NFL document.

Declared sources

Every URL this project reads is declared in pipeline/nfl_sources.py with its provenance chain back to the NFL, what was actually observed when it was probed, and its licence note. If a URL is not in that registry it is not used.

Direct from nfl.com

The charter for this project asks for data straight from the NFL. api.nfl.com — the league's own API — is reachable but answers HTTP 401 without a credential the NFL issues only to its own site and to contracted partners, and the old nfl.com/liveupdate feeds are decommissioned. What is still open, unauthenticated and produced by the league is the website itself: nfl.com/schedules. Each game tile there carries the NFL's own score and status text next to the canonical /games/ URL.

This build reads that page and compares it with what is published here. A disagreement is shown below rather than hidden. The read has one narrow, honest job: it confirms or contradicts the published scores, and it can mark a game Final when the league says it is over even if this project's clock estimate still had it in progress. It never supplies play-by-play, and its numbers are never merged into the archive — they are kept as their own artefact so the two can always be told apart.

If the read fails, the snapshot says so. A page that could not be fetched or parsed is recorded as unavailable; it is never treated as agreement, and an empty result is never reported as a success.

Method notes

How game status is decided
  1. If the play-by-play contains an official GAME_END play, status is Final and is marked as not estimated. This is authoritative.
  2. Otherwise, if upstream publishes both scores, status is derived from the kickoff clock: within 4h45m of kickoff it reads Live (est.), after that Final. Anything derived this way carries status_estimated: true and the UI shows “(est.)”.
  3. If no score is published and kickoff is in the future, status is Scheduled.
  4. If no score is published and kickoff is more than 4h45m in the past, status is Unknown and the record is flagged past-window-without-score. A cancelled or postponed game and a lagging feed look identical from the data, so the pipeline refuses to choose between them.

Kickoff times in the upstream feed are US Eastern, converted to UTC using the America/New_York zone so daylight saving is handled. If the timezone database is unavailable the pipeline records kickoff_time_known: false rather than guessing an offset.

How the quarter-by-quarter line is derived
Taken from the running score published on each official play (total_home_score / total_away_score). Each quarter's points are the difference from the previous quarter's running total. Quarters with no scored plays upstream are omitted rather than shown as zero. The line is cross-checked against the scheduled final score and any disagreement is flagged.
How team statistics are aggregated
Every team and player figure on a game page is a sum of the per-play values published upstream. Nothing is modelled, projected or estimated. Fields the feed does not publish for a game (for example time of possession on older seasons) render as —.
How the direct read of nfl.com works
The pipeline fetches nfl.com/schedules/{season}/by-week/{week} for the most recent weeks and reads the score and status nfl.com prints for each game. Two passes run over the page: every game link with the most informative accessible name near it, then every canonical game slug anywhere in the markup. The second pass exists because the first is provably not enough — the 2026 week-3 international game (Ravens at Cowboys, Rio de Janeiro) is rendered differently and was missed, so that week's slate came back one game short. A page the league renders in a different template must never quietly shrink the comparison.
Why some links are hidden
pipeline/verify_links.py fetches the nfl.com URLs this project constructs and records the real HTTP outcome. A link that did not resolve is hidden and reported below, because a link to a 404 is worse than no link. Links that were not sampled are still shown: the URL pattern itself was verified against live nfl.com pages.
